# План реализации и проверки

## Как использовать план

Порядок ниже является обязательным. Он не содержит календарных оценок: сроки
зависят от согласования дизайна, данных, платформы и ответственных лиц.
Следующий этап не начинается только потому, что предыдущий визуально выглядит
готовым. Нужны все указанные criteria выхода.

| Этап | Результат | Начинать после | Criteria выхода |
| --- | --- | --- | --- |
| 0 | Передача проекта и подготовка контуров | Сейчас | Документы изучены, Git и CI спланированы, решения зафиксированы |
| 1 | Миграция публичной вёрстки в Next.js | Утверждены макеты и контент для UI | Семантический, адаптивный, доступный UI без бизнес-данных |
| 2 | PostgreSQL и первая модель каталога | Согласован `CATALOG_RFC` и staging база | Миграции, backup/restore, schema tests и review пройдены |
| 3 | Excel import v1 | Этап 2 и Excel-правила подтверждены владельцем | Preview, confirmation, audit, lock, idempotency и rollback проверены |
| 4 | Админка приложения и товарные фото | Утверждены модель ролей, storage и auth | Server-side права, безопасная загрузка и журналирование проверены |
| 5 | Headless WordPress для контента | Утверждены content model и отдельный WordPress контур | Публикация контента без доступа CMS к каталогу или приложению |
| 6 | Публичный каталог и SEO | Этапы 2-5 дают проверенные данные | Category/product routes, SEO и публичный API проверены |
| 7 | Заявка, корзина, wishlist, кабинет | Утверждены политика данных, auth и бизнес-правила | Серверная проверка цены и прав, privacy и E2E сценарии пройдены |
| L | Бонусы и Telegram, отдельный Core | ADR-0003, PostgreSQL, общий вход владельцев, `LOYALTY_MVP_RFC` и `LOYALTY_TECHNICAL_SPEC` | Idempotency, account-level audit, Telegram delivery и rollback проверены |
| 8 | Интеграция с 1С | Стабильный каталог и утверждённый контракт 1С | Staging sync, конфликт-отчёт и rollback проверены |

## Этап 0. Передача и инфраструктурная готовность

### Сделать

- Принять правила из `AGENTS.md` как обязательный контракт.
- Создать Git-репозиторий и CI, не меняя history существующих материалов.
- Проверить отдельной read-only задачей хостинг: Node.js 24.x, process manager,
  reverse proxy с HTTPS, PostgreSQL, сеть базы, secret storage, backup/restore,
  staging и мониторинг.
- Зафиксировать решения из [OPEN_DECISIONS.md](OPEN_DECISIONS.md).
- Согласовать owner для кода, контента, каталога, импорта и release.

### Проверить

- `npm run check` на Node.js 24.19.0 или новой версии ветки 24.x.
- `npm audit --audit-level=high --engine-strict`.
- Отсутствие секретов в репозитории, инструкциях и CI logs.
- Наличие плана восстановления базы, не только факта создания backup.

### Нельзя

- Подключать production базу, Excel, WordPress, Telegram или 1С.
- Деплоить legacy `dist` или `.deploy` на production.

## Этап 1. Миграция вёрстки

### Сделать

- Реализовать только утверждённые публичные макеты в `src/app` и
  `src/components`.
- Использовать Sass по смысловым блокам, tokens и BEM-подобные имена.
- Вынести повторяемые UI-иконки в `src/assets/icons/sprite.svg`.
- Сохранить и проверить SEO-файлы, canonical strategy и verification files.
- Добавить визуальные snapshots и accessibility проверки для ключевых
  viewport.

### Проверить

- Desktop, tablet и mobile макеты, включая keyboard navigation и `:focus-visible`.
- Один `h1` на страницу, правильную семантику ссылок, кнопок и изображений.
- Отсутствие layout shift от изображений и работа без JavaScript там, где
  интерактивность не нужна.
- Никаких production-карточек товаров, цен, остатков, корзины или источника
  данных каталога. Визуальные fixtures допустимы только по разделу 1.3
  `AGENTS.md`: для локальной и staging-приёмки вёрстки, без реальных данных,
  внешних вызовов, сохранения или заявления о создании заявки.

### Нельзя

- Придумывать отсутствующий legacy дизайн.
- Копировать HTML, Sass или SVG из `S:\rampa\otel`; применяется только его
  подход к структуре компонентов, классам и спрайту.

## Этап 2. Модель каталога и PostgreSQL

### Сделать

- Утвердить [CATALOG_RFC.md](CATALOG_RFC.md) до создания таблиц.
- Поднять отдельную local/test/staging PostgreSQL базу.
- Создать миграции только через `node-pg-migrate`.
- Реализовать constraints, foreign keys, unique keys, checks, ownership
  imported and manually edited fields.
- Подготовить seed исключительно из синтетических данных.

### Проверить

- Новая миграция применима на чистой базе.
- Миграция проверена на staging copy, с оценкой locks и времени.
- Backup восстановлен в изолированном окружении.
- Миграция не меняет внутренний ID, URL и связи при обновлении товара.
- Негативные тесты constraints проходят.

### Нельзя

- Менять production schema вручную.
- Использовать название, строку Excel или будущий GUID 1С как primary key.
- Физически удалять товары как реакцию на отсутствие в импортируемом файле.

## Этап 3. Контролируемый Excel import v1

### Сделать

- Реализовать только адаптер `greenmarket-price-v1` по
  [EXCEL_IMPORT_SPEC.md](EXCEL_IMPORT_SPEC.md).
- Хранить исходный файл вне public directory под случайным именем.
- Разделить upload, parsing, normalization, validation, preview, confirmation,
  transaction и audit.
- Ввести lock для конфликтующих импортов.
- Сделать подтверждённую карту server-side сопоставлений без Excel ID.

### Проверить

- Повторный импорт не создаёт дубли.
- Строка без названия, невалидная цена, неизвестная доступность и
  неоднозначное сопоставление не публикуются автоматически.
- Ошибка одной фотографии отсутствует как сценарий, поскольку v1 не принимает
  фотографии из Excel.
- Ошибка записи откатывает каталог и оставляет понятный audit status.
- В preview есть added, changed, unchanged, skipped, errors и manual review.

### Нельзя

- Считать пустое название продолжением предыдущей строки.
- Использовать fuzzy matching или автоматически объединять похожие названия.
- Деактивировать товары из-за отсутствия строки в partial import.

## Этап 4. Админка приложения и товарные фотографии

### Сделать

- Реализовать authentication и roles только после выбора модели в
  `OPEN_DECISIONS.md`.
- Разделить права import manager, product media editor и administrator.
- Добавить отдельное storage для оригиналов и подготовленных производных.
- Хранить связь фото только с внутренним `product_id`.
- Сделать immutable audit для импортов, ручных mappings и изменений фото.

### Проверить

- Проверка прав производится сервером для каждого объекта и действия.
- Upload проверяет signature, MIME, размер, dimensions, filename и SVG policy.
- Public URL отдаёт только подготовленную безопасную производную, без лишнего EXIF.
- Повторный Excel import не изменяет cover, sort order и alt товарных фото.
- Удаление файла возможно только после безопасного отвязывания и policy retention.

## Этап 5. WordPress headless для редакционного контента

### Сделать

- Развернуть WordPress отдельно: отдельная база, credentials, backup и update policy.
- Создать минимальный проектный plugin с content types и REST representation.
- Настроить Next.js server-side content layer и cache invalidation.
- Ограничить WordPress published content и медиа его контентных сущностей.

### Проверить

- CMS не имеет credentials к PostgreSQL приложения.
- Browser не получает WordPress privileged credentials.
- Черновики и служебные поля не попадают в публичный API.
- Security policy, allowlist доменов CMS и медиа согласованы до production.

## Этап 6. Публичный каталог и SEO

### Сделать

- Выдавать каталог только из PostgreSQL через server-side application layer.
- Реализовать routes: категории, товар, поиск и фильтры только после
  согласования UX и индексов.
- Генерировать title, description, canonical, Open Graph, breadcrumbs и
  structured data на сервере.
- Явно определить policy показа отсутствующих и товаров без фото.

### Проверить

- Цены и доступность в ответах сервера согласованы с БД.
- Страница товара не раскрывает import audit, внутренние ID или черновые поля.
- Sitemap, robots, canonical и redirect strategy проверены на staging.
- Нагрузочные и query plans проверены для реальных сценариев поиска и категорий.

## Этап 7. Торговые пользовательские функции

### Сделать

- Сначала утвердить privacy policy, набор собираемых данных, сроки хранения,
  уведомления и правила удаления.
- Реализовать заявку либо корзину, затем wishlist, затем кабинет.
- Все цены, остатки, скидки, totals и права пересчитывать на сервере.

### Проверить

- CSRF, rate limiting, validation, authz и object ownership.
- Повторный запрос не создаёт дубли заявок или списаний.
- E2E: гость, пользователь, сотрудник, отказ в доступе, ошибка внешнего
  уведомления, retry и восстановление.

## Параллельный контур L. Бонусы и Telegram

### Сделать

- Утвердить [LOYALTY_MVP_RFC.md](LOYALTY_MVP_RFC.md),
  [LOYALTY_TECHNICAL_SPEC.md](LOYALTY_TECHNICAL_SPEC.md) и закрыть оставшиеся
  решения раздела 12 ТЗ до первой миграции.
- Слой L0: чистые серверные расчёты без базы, Telegram и персональных данных.
- Утвердить [ADR-0003](adr/0003-loyalty-core-service.md) и создать отдельный
  `greenmarket-core` до реализации API или админки.
- После PostgreSQL и общего входа владельцев: клиенты, immutable ledger,
  кассовые экраны, затем Telegram-привязка и outbox уведомлений.

Контур L не ждёт Excel-import, WordPress, публичный каталог, корзину или 1С.
Он не может перейти дальше L0 до PostgreSQL, Core и общего входа владельцев в
бонусный раздел.

### Проверить

- Unit-тесты ставки, округления, лимита 50%, совместного списания и начисления,
  партий, дня рождения и идемпотентности.
- Повторная отправка формы не начисляет бонусы второй раз.
- Списание только через общий авторизованный аккаунт в физической кассе при
  личном присутствии клиента.
- L0 не имеет импорта из базы, HTTP-обработчиков, Telegram-вызовов, секретов,
  персональных данных или импорта в публичные страницы.
- Telegram не создаёт ledger-операции. Сбой бота не откатывает кассу.
- Одна кассовая операция создаёт не более одного Telegram-уведомления.

## Этап 8. Интеграция с 1С

### Сделать

- Описать контракт, credentials, поле ownership и failure handling для 1С.
- Создать 1С adapter, использующий ту же внутреннюю модель, что и Excel import.
- Выполнить первое сопоставление с 1С только на staging, с отчётом и ручным
  подтверждением конфликтов.

### Проверить
- 1С outage не мешает открытию сайта.
- Полная staging sync сверена по товарам, offers, ценам, остаткам, категориям,
  фото и количеству конфликтов.

## Общий gate перед каждым release

- Review complete diff.
- Выполнить обязательные CI checks.
- Применить migration только после backup и проверенного rollback plan.
- Сначала staging, затем production.
- Проверить public routes, `/api/health`, headers, error handling и monitoring.
- Зафиксировать фактический результат и непроверенные области.
