# Green Market: целевой стек и правила развития

Документ фиксирует целевую архитектуру проекта. Бывший Vite + React прототип
заменён на основу Next.js + React + TypeScript. В ней пока нет бизнес-функций
магазина. Для промышленной версии интернет-магазина целевым направлением
остаются серверная база данных, безопасный импорт каталога из Excel и
отдельная админка для контента.

## 0. Статус, порядок решений и переход к production

### Основа production-приложения

В репозитории есть foundation на Next.js 16.3, React 19, TypeScript strict,
Sass, Zod, PostgreSQL migration tooling и Vitest. Он ограничен статическим
публичным UI, безопасным health endpoint и инфраструктурными проверками.
Foundation не означает готовность каталога или разрешение подключать реальные
данные и сервисы.

До отдельной задачи соответствующего этапа foundation не должен:

- получать, хранить, передавать или логировать реальные пользовательские и коммерческие данные;
- реализовывать авторизацию, роли, админку, оформление заявок, оплату, бонусы, цены, остатки, корзину или wishlist;
- обращаться к production-базе, Excel, 1С, CMS, Telegram, почте и любым внешним сервисам;
- содержать реальные секреты, внешние credentials, proxy-обходы или источник
  истины для бизнес-данных.

Нельзя добавлять бизнес-логику в браузер или подменять отсутствующий сервер
`localStorage`, статическим JSON, моками или фиктивным успешным ответом.
Для приёмки утверждённой вёрстки допустимы только визуальные fixtures по
правилам раздела 1.3 `AGENTS.md`: без реальных данных, сетевых вызовов,
сохранения, логирования или заявления о создании заявки. Они не являются
частью production-каталога и должны быть заменены серверной реализацией на
соответствующем этапе.
Следующая задача после foundation: не публикация сайта, а утверждение модели
каталога, схемы первой миграции, границ импорта и сценариев админ-доступа.

### Иерархия решений

- `AGENTS.md` устанавливает обязательные требования к безопасности, данным, проверкам и действиям агента.
- Этот документ определяет утверждённый план продукта и архитектурные границы.
- Агент не реализует возможность, которой нет в текущем этапе, и не выбирает сам технологии с существенной стоимостью, vendor lock-in, обработкой персональных данных или влиянием на доступ.
- Если для этапа не определены существенные детали, например провайдер авторизации, хостинг, модель ролей, способ платежа или состав персональных данных, реализация останавливается до решения владельца проекта.

### Условие начала production-разработки

Перед первой production-функцией должны быть утверждены и проверены:

1. Next.js + TypeScript с включённой строгой типизацией.
2. Разделение публичного UI, серверной бизнес-логики, доступа к данным и интеграций.
3. PostgreSQL, миграции, отдельные конфигурации development, test, staging и production.
4. Проверка конфигурации при запуске, хранение секретов вне репозитория и безопасные значения по умолчанию.
5. Контроль доступа на сервере, обработка ошибок без раскрытия внутренней информации, аудит и тестовый контур.
6. CI-проверки: type check, lint, тесты, production build, проверка миграций и аудит случайно добавленных секретов.

До выполнения этих условий результат может называться только прототипом. Публичный production-релиз функций, затрагивающих пользователей, данные или деньги, запрещён.

## 1. Цели проекта

- Публичный сайт садового центра с каталогом, статьями, новостями, акциями и SEO-страницами.
- Каталог товаров сначала обновляется из Excel, позже должен быть готов к интеграции с 1C.
- Новости, статьи, слайдеры, баннеры и контентные страницы редактируются через админку.
- Корзина, wishlist, личный кабинет и бонусная система добавляются поэтапно.
- Архитектура не должна зависеть от Excel как постоянного источника данных.

## 2. Целевой стек

### Frontend

- Next.js + React.
- TypeScript для нового production-кода.
- Sass-модули по компонентам: отдельный файл на смысловой блок, центральные токены и явное подключение модулей без глобального хаоса.
- Классы BEM-подобные: блок `catalog-card`, элемент `catalog-card__title`, модификатор `catalog-card--compact`, интерактивное состояние `is-active`.
- Серверный рендеринг или статическая генерация для публичных SEO-страниц.

Повторно используемые UI-иконки размещаются в едином SVG-спрайте `src/assets/icons/sprite.svg` и вызываются через `<use>` с `currentColor`. В спрайт не помещаются пользовательские загрузки, фотографии, уникальные иллюстрации и одиночные логотипы. Все SVG-пути в спрайте проходят проверку происхождения и не содержат скриптов, внешних ссылок или активного содержимого.

Почему Next.js:

- поисковики и мессенджеры получают готовый HTML для товаров, категорий, статей и акций;
- у каждой сущности есть стабильный URL;
- проще совмещать публичные страницы, интерактивные элементы и серверные операции;
- удобнее развивать проект до полноценного магазина без отдельного frontend-костыля.

### Backend

- Серверная часть обязательна для каталога, заявок, бонусов, пользователей и интеграций.
- API сайта читает данные только из базы приложения.
- Клиент не обращается напрямую к Excel, 1C, базе данных или внешним каталогам.
- Вся бизнес-логика цен, остатков, бонусов и прав доступа выполняется на сервере.

Рекомендуемый вариант:

- Next.js для публичного сайта и части серверных API.
- Отдельный backend-сервис допускается, если логика импорта, бонусов и интеграций станет крупной.

### База данных

- PostgreSQL как основная база приложения.
- Денежные значения хранить в минимальных единицах, например в копейках, либо в точном decimal-типе.
- Все изменения схемы выполнять через миграции.
- Production-каталог не хранить в коде, статическом JSON, JavaScript-массивах или localStorage.

### Админка и CMS

Основная рекомендация: WordPress в headless-режиме.

WordPress использовать для:

- новостей;
- статей;
- слайдеров главной страницы;
- баннеров;
- акций;
- SEO-полей;
- контентных страниц;
- медиатеки изображений статей, новостей, баннеров и слайдеров.

WordPress не является источником истины каталога, заменой сервиса импорта или местом ручного исправления полей, которыми владеет Excel или будущая 1С. Продукты создаёт и обновляет только серверный сервис импорта. WordPress не хранит товары, цены, остатки, заявки, бонусы или пользовательские данные приложения.

Фотографии товаров не хранятся в WordPress: они относятся к каталогу и управляются в защищённой админке приложения. В PostgreSQL создаётся отдельная связь `product_images`: `product_id`, идентификатор файла в объектном или файловом хранилище, порядок, признак обложки и alt-текст. Excel не содержит изображения и не изменяет эту связь. Поэтому повторный импорт не удалит вручную добавленные фотографии.

Роли в админке разделяются:

- редактор WordPress управляет статьями, новостями, слайдерами, баннерами, акциями, SEO и медиа этих материалов;
- редактор фотографий товаров работает только в админке приложения: может загружать файлы в выделенное хранилище и менять только `product_images`;
- менеджер импорта работает с Excel через серверный интерфейс приложения, а не через WordPress;
- публичная роль не имеет доступа к черновикам, админке, журналам импорта, исходным файлам и API-методам, которые возвращают непубличный контент.

WordPress развёртывается отдельно, со своей базой данных и отдельными credentials. Он не получает доступ к PostgreSQL приложения. Публичный сайт получает опубликованный контент и изображения через серверный слой Next.js, а не через привилегированный доступ из браузера. Секреты WordPress, пароли приложений и cookie админки не передаются браузеру.

WordPress-плагины:

- использовать только необходимые поддерживаемые плагины с зафиксированными версиями и планом обновления;
- не использовать WooCommerce, page builder, плагины произвольного кода, импорта Excel, доступа к базе приложения, прямой интеграции с 1С или «универсальные» плагины без проверки;
- пользовательские типы записей, поля, REST-представление и webhook-интеграции реализовывать минимальным проектным плагином в репозитории, а не набором несовместимых расширений;
- WordPress REST API для контента ограничивать опубликованными полями и записями. Изменяющие запросы выполняются только аутентифицированными ролями по HTTPS с проверкой прав и CSRF-защитой админки.

Причина выбора WordPress: рынок специалистов и контент-редакторов шире, а его административный интерфейс привычнее. Этот плюс не должен менять границу данных: WordPress обслуживает редакционный контент, а приложение обслуживает каталог и бизнес-операции.

## 3. Архитектура данных каталога

Обязательное направление данных:

```text
Excel (.xlsx) ----\
                  -> адаптер источника -> единая модель -> валидация -> база данных -> API -> сайт
1C API -----------/
```

Сайт, корзина, wishlist, поиск и страницы товаров читают каталог только через серверный API из базы данных.

### Внутренние и внешние идентификаторы

- У каждого товара есть внутренний неизменяемый `product_id`.
- Внешний ID из Excel не требуется. GUID 1С, если появится, не является primary key товара.
- Связка источников хранится отдельно: `source`, `source_file_hash`, `sheet_name`, `row_number`, `row_fingerprint`, `product_id`, `offer_id`, `mapping_status`.
- Переход с Excel на 1C не должен менять URL товара, связи корзины, wishlist и историю заявок.
- `row_fingerprint` без внешнего ID создаётся сервером из точной нормализованной комбинации категории, названия, контейнера или возраста и размера. Это служебная метка журнала импорта, а не поле Excel, не primary key и не идентификатор товара.
- Автоматически объединять товары по похожему названию запрещено. Неоднозначный или изменившийся `row_fingerprint` останавливает автоматическое обновление строки и требует ручного решения в предварительном отчёте.

### Входная модель импорта

Минимальная модель товара:

```ts
interface CatalogProductInput {
  name: string
  categorySourceKey: string
  containerOrAge?: string
  plantSize?: string
  description?: string
  priceMinor: number
  availabilityNote?: string
  tags: string[]
}
```

Модель может расширяться, но не должна содержать детали Excel-библиотеки или внутренней структуры 1C. Фотографии не входят в текущий Excel-импорт: они управляются через отдельную сущность `product_images` в админке приложения.

## 4. Excel-импорт

Excel используется только как источник импорта, а не как runtime-база сайта.

Поддерживаемый формат:

- `.xlsx`;
- отдельный ID и артикул не требуются;
- обязательные данные строки: название, цена и категория из листа;
- контейнер, возраст, размер и расширенные характеристики могут быть пустыми, но строка с неуникальным набором данных не обновляется автоматически;
- порядок колонок не имеет значения;
- сопоставление выполняется по нормализованным заголовкам.
- колонки, встроенные изображения, URL и архивы с фотографиями не поддерживаются.

### Исходный прайс для первичного переноса

Файл `Для сайта Прайс ГринМаркет.xlsx` от 13 августа 2026 года принят как исходный прайс для первого контролируемого переноса. В нём 12 листов: плодовые, хвойные, вересковые, гортензии, розы, кустарники и деревья, многолетники, пряные травы, злаки и травы, луковичные, лианы и сопутствующие товары.

Этот файл не является регулярным импортным шаблоном:

- в нём отсутствует отдельный ID и единый артикул, это допустимо;
- строки заголовков и набор колонок различаются между листами;
- перед таблицами есть служебный текст и контакты;
- наличие, контейнеры и размеры хранятся как свободный текст;
- есть строки с ценой и контейнером, но без названия, поэтому нельзя безопасно делать автоматическое наследование значений из соседней строки;
- фотографий в файле нет.

После окончания подготовки файла для него создаётся отдельный серверный адаптер `greenmarket-price-v1`. Он читает только зафиксированную схему разрешённых листов и колонок, сохраняет номер листа и строки в журнале и всегда показывает предварительный отчёт. Строки без названия, нераспознанные статусы наличия, некорректные цены и неоднозначные данные блокируют автоматическую публикацию и требуют ручного решения.

Первый импорт создаёт внутренние `product_id` и сохраняет подтверждённую карту соответствий с внутренним серверным `row_fingerprint`. Повторная загрузка может предложить обновление только при точном совпадении этой служебной метки с одной ранее подтверждённой связью. Изменённые или неоднозначные строки не обновляются автоматически, не объединяются по похожему названию и требуют подтверждения. Отдельный ID в Excel для этого не нужен.

Процесс импорта:

1. Загрузка файла администратором.
2. Проверка расширения, MIME-type, сигнатуры, размера и лимитов обработки.
3. Парсинг в промежуточную структуру.
4. Нормализация значений.
5. Полная серверная валидация.
6. Предварительный просмотр изменений.
7. Явное подтверждение администратором.
8. Транзакционное применение.
9. Журнал импорта и отчет.

До подтверждения нельзя менять рабочий каталог.

Импорт не создаёт, не обновляет и не удаляет фотографии. Он не должен отменять или менять вручную установленную обложку, порядок и alt-текст даже при обновлении или деактивации товара.

Импорт должен показывать:

- сколько товаров будет добавлено;
- сколько обновлено;
- сколько деактивировано;
- сколько пропущено;
- сколько строк содержит ошибки.

Ошибки должны содержать номер строки, поле и безопасное понятное описание.

## 5. Контент сайта

Через админку редактируются:

- статьи;
- новости;
- слайдер главной страницы;
- баннеры;
- акции;
- SEO title и description;
- текстовые блоки категорий;
- изображения контентных страниц.

Контент не должен быть захардкожен в React-компонентах, если его должен менять администратор.

### Фотографии товаров

После успешного импорта товара редактор фотографий открывает защищённый раздел админки приложения, загружает одну или несколько фотографий и связывает их с внутренним `product_id`. Связь хранит `file_id`, порядок, обложку и alt-текст. Название, контейнер, размер, цена и номер строки Excel не используются как единственная связь фотографии с товаром.

Файлы загружаются только в выделенную медиатеку. До публикации они проходят проверку фактического формата, размера и габаритов; допустимые MIME-type и лимиты утверждаются в production-конфигурации. Оригиналы остаются закрытыми, а публичный сайт использует только подготовленные производные изображения без ненужных EXIF-данных.

Товар без фотографии не ломает импорт. Политика публикации такого товара утверждается отдельно до запуска каталога: нельзя неявно заменять отсутствие фото чужим изображением или изображением, которое выглядит как фотография товара.

## 6. SEO-правила

Для публичных страниц обязательно предусмотреть:

- уникальный URL;
- `title`;
- `description`;
- один основной `h1`;
- человекочитаемый slug;
- canonical URL;
- Open Graph данные для мессенджеров;
- alt для значимых изображений;
- микроразметку товара, статьи и хлебных крошек, когда это применимо.

SEO-поля редактируются в админке, но отдаются сайтом как готовый HTML через Next.js.

## 7. Бонусная система

Бонусная система хранится на сервере в PostgreSQL. Telegram-бот является
необязательным кабинетом, не источником истины и не может начислять, списывать
или корректировать бонусы. Полная граница MVP, угрозы, данные, проверки и
незакрытые правила описаны в [LOYALTY_MVP_RFC.md](LOYALTY_MVP_RFC.md) и
[LOYALTY_TECHNICAL_SPEC.md](LOYALTY_TECHNICAL_SPEC.md).

До появления PostgreSQL, ролей и защищённой админки разрешён только L0:
чистые серверные функции политики, денег, партий, дня рождения и проекции
кабинета с unit-тестами. Он не выполняет I/O, не работает с базой, Telegram,
HTTP, секретами или реальными персональными данными.

## 8. Личный кабинет, wishlist и корзина

Рекомендуемый порядок внедрения:

1. PostgreSQL и защищённый доступ сотрудников к админке.
2. Параллельно:
   - каталог, Excel-import, фото товаров, WordPress и публичные страницы;
   - бонусный ledger, кассовый интерфейс и Telegram-бот.
3. Заявка или корзина без полноценного личного кабинета.
4. Wishlist с сохранением в базе для авторизованных пользователей.
5. Личный кабинет: профиль, wishlist и история заявок.
6. Интеграция с 1C.

Wishlist без регистрации можно использовать только как временное удобство на устройстве пользователя. Для надежного сценария wishlist должен храниться в базе и быть привязан к пользователю.

## 9. Безопасность и данные

- Авторизация и права проверяются только на сервере.
- Роль, user ID, цена, скидка, сумма заказа и бонусы не принимаются от клиента как доверенные данные.
- Секреты хранятся только в переменных окружения или secret manager.
- В production приложение должно падать при отсутствии обязательной конфигурации.
- Логи не должны содержать телефоны, email, адреса, токены, cookie и содержимое заявок в открытом виде.
- Для cookie использовать `HttpOnly`, `Secure`, `SameSite`.
- Для загрузок файлов нужны ограничения размера, формата и времени обработки.

## 10. Этапы развития

### Этап 1. Основа

- Зафиксировать стек.
- Перенести production-направление на Next.js + TypeScript.
- Подготовить модель данных каталога и контента.

### Этап 2. Каталог

- PostgreSQL.
- API каталога.
- Безопасный импорт `.xlsx`.
- Предпросмотр и журнал импортов.

### Этап 3. Контент

- WordPress в headless-режиме.
- Новости, статьи, слайдеры, акции, SEO-поля.
- Публичные страницы с готовым HTML.

### Этап 4. Торговые функции

- Корзина или заявка.
- Wishlist.
- Базовый личный кабинет.

### Параллельный контур: бонусы

- Серверная модель бонусов.
- Админский ввод покупок.
- Telegram-бот для клиента, просмотра баланса и отправки копии бонусной операции.

### Этап 6. Подготовка к 1C

- Отдельный адаптер 1C.
- Контролируемое сопоставление внутреннего `product_id` сайта и GUID 1C через отдельную явную таблицу.
- Тестовая синхронизация на staging.
- Переключение источника только после отчета и проверки.

## 11. Что пока не делаем

- Не подключаем реальные бизнес-функции и интеграции, пока не утверждены их
  серверная модель, права доступа, миграции, тесты и план отката.
- Не читаем Excel на каждой странице сайта.
- Не храним каталог в frontend-коде.
- Не загружаем и не связываем фотографии товаров через Excel.
- Не даём редакторам WordPress изменять поля товара, которыми владеет импорт, или выполнять импорт Excel.
- Не используем WooCommerce и WordPress как каталог, корзину, базу цен, заявок, бонусов или пользователей приложения.
- Не делаем 1C обязательной для открытия сайта.
- Не делаем бонусы только в Telegram без серверной базы.
- Не смешиваем ручное редактирование контента и импортируемые товарные поля без правил владения.
- Не начинаем с большого личного кабинета до появления каталога, заявок и базовой авторизации.
