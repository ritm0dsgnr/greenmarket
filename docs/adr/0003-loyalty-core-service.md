# ADR-0003: отдельный сервис для бонусов, админки и Telegram

## Статус

Принято владельцем 17 августа 2026 года: создаётся закрытый репозиторий
`greenmarket-core`. Документ не подключает production-данные и Telegram.

## Контекст

Публичный сайт `greenmarket` является Next.js-приложением для посетителей.
Контур бонусов обрабатывает номера телефонов, согласия, бонусные операции,
сессии административного доступа и Telegram-связи. Эти данные и операции не
должны находиться в public-приложении, WordPress или браузере.

Контур включает три исполнения одной бизнес-системы:

1. защищённую админку для общей учётной записи трёх владельцев;
2. серверное API и PostgreSQL-логику;
3. Telegram webhook в API и worker доставки уведомлений.

Они используют одну модель данных и одну транзакционную outbox-очередь.
Разделять их по независимым репозиториям означает дублировать контракты,
секреты и правила идемпотентности.

## Рассмотренные варианты

1. Реализовать бонусы внутри public-репозитория `greenmarket`. Отклонено:
   public-сайт и административный контур получают общий релиз, общие
   зависимости и повышенный риск случайного доступа к персональным данным.
2. Сделать отдельный сервис для каждого компонента: API, админка и бот.
   Отклонено для MVP: повышается сложность разработки и доставки, а единый
   ledger всё равно требует общей доменной модели и PostgreSQL.
3. Создать отдельный репозиторий `greenmarket-core` с несколькими
   приложениями. Рекомендовано: public-сайт отделён, а API, админка и worker
   остаются одной проверяемой системой.

## Рекомендованное решение

Создать отдельный закрытый репозиторий `greenmarket-core`.

```text
greenmarket                    public website
  Next.js
  no direct PostgreSQL access
  server-to-server read calls only when catalog API appears

greenmarket-core               business system
  admin application
  API application
  Telegram webhook and outbox worker
  PostgreSQL migrations and domain rules

WordPress                      editorial CMS
  separate database and credentials
  no access to core PostgreSQL
```

`greenmarket-core` использует один monorepo на `npm workspaces`:

```text
apps/
  admin/       protected administrative UI
  api/         HTTP API and authentication boundary
  worker/      outbox delivery
packages/
  domain/      pure loyalty rules, moved from L0
  contracts/   Zod request and response schemas
  db/          pg repositories and node-pg-migrate migrations
```

В production это три отдельных процесса с отдельными runtime credentials:
`admin`, `api` и `worker`. Они могут быть развёрнуты на одной платформе, но
worker не является частью browser bundle, а PostgreSQL не публикуется в
интернет.

## Границы данных и доступа

- Только `greenmarket-core` имеет права записи в бонусные таблицы PostgreSQL.
- Public-сайт не получает строку подключения к PostgreSQL, Telegram token,
  cookie админки или права на бонусные операции.
- WordPress использует отдельную базу и не подключается к PostgreSQL
  `greenmarket-core`.
- Браузер админки работает только через защищённый origin админки. Он не
  обращается к PostgreSQL, Telegram или объектному хранилищу напрямую.
- Telegram webhook принимает только `api`, проверяет HTTPS, секретный
  заголовок и идемпотентность `update_id`.
- `worker` читает outbox-таблицу и не принимает HTTP-запросы посетителей.
- Технические credentials `api`, `worker`, PostgreSQL, object storage и
  Telegram всегда отдельные. Один общий пароль владельцев относится только к
  человеческому входу в админку.

## Общая учётная запись владельцев

В MVP три продавца-владельца используют один аккаунт `loyalty_admin` с одной
ролью и полным доступом к бонусному разделу. Иерархия ролей не нужна.

Это осознанное организационное ограничение: система может подтвердить действие
общего аккаунта, но не может технически установить, кто из трёх людей выполнил
операцию. Поле аудита называется `performed_by_admin_account_id`, а не
`staff_id` или `author_id`.

Обязательные компенсирующие меры:

- пароль уникален, хранится только в согласованном password manager;
- пароль не передаётся в чатах и не записывается в браузерных заметках;
- для аккаунта включаются доступные passkeys или второй фактор с
  зарегистрированными устройствами владельцев;
- сессия имеет ограниченный срок и все сессии отзываются при утрате устройства,
  уходе владельца или подозрении на раскрытие пароля;
- вход и поиск телефона имеют rate limit;
- доступ к админке разрешён только по HTTPS;
- журнал отображает общий аккаунт, время, объект, причину и серверный
  идентификатор операции, но не утверждает личность конкретного владельца.

## Миграция и откат

До появления реальных данных допустимо удалить весь test-контур и выполнить
`db:down` только в local/test. После первой бонусной операции откат данных
выполняется только новой компенсирующей операцией и forward-миграцией.

Public-сайт не зависит от запуска `greenmarket-core`, пока не подключён
catalog API. Недоступность Telegram не отменяет зафиксированную кассовую
операцию.

## Последствия

- Для backend-разработки появляется отдельный репозиторий и независимый
  lifecycle release.
- Бизнес-правила L0 переносятся в `packages/domain`, а не копируются между
  сайтом, админкой и ботом.
- Прежде чем создать репозиторий и migration, владелец подтверждает это ADR,
  hosting capabilities, privacy policy, retention и storage secrets.
