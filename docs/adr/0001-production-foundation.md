# ADR-0001: Основа production-приложения

## Статус

Принято 13 августа 2026 года.

## Контекст

Предыдущая кодовая база Vite + React + JavaScript была визуальным прототипом.
В ней не было серверной границы, проверки runtime-конфигурации, механизма
миграций базы данных и автоматических проверок, необходимых для каталога,
импорта, контроля доступа или персональных данных.

Утверждённый план требует публичный сайт с серверным рендерингом, PostgreSQL,
безопасный импорт Excel и отдельную границу WordPress для редакционного
контента. Первый production-этап не должен добавлять данные каталога,
пользовательские данные, авторизацию, внешние интеграции или изменения
хостинга.

## Рассмотренные варианты

1. Продолжать развивать Vite-прототип. Отклонено: для будущей бизнес-логики и
   данных не появится необходимая серверная граница.
2. Ввести отдельный backend, сохранив Vite публичным приложением. Отклонено
   для первого этапа: это создаёт дополнительную границу развёртывания до
   появления конкретной интеграции или бизнес-сценария, которому она нужна.
3. Перейти на Next.js с типизированной серверной границей и подготовить
   миграции PostgreSQL. Выбрано.

## Решение

Использовать следующую основу production-приложения:

- Next.js 16.3 с React 19.2 и App Router;
- TypeScript 5.9 в строгом режиме;
- Sass с существующими BEM-подобными соглашениями для компонентов;
- PostgreSQL через `pg`, изменения схемы через `node-pg-migrate`;
- Zod для явной проверки server-side переменных окружения;
- ESLint и Vitest как исходный контур статического анализа и unit-тестов.

На этом этапе приложение остаётся статической публичной оболочкой. Единственный
публичный runtime endpoint, `/api/health`, неаутентифицирован, не принимает
чувствительные данные и не обращается к базе, Excel, WordPress или внешним
сервисам.

WordPress остаётся будущей отдельной headless CMS только для редакционного
контента. Он не устанавливается, не настраивается и не подключается в рамках
этого решения.

## Границы данных и доступа

- Код браузера может только отображать публичный UI и вызывать публичные
  маршруты приложения.
- Production-конфигурацию читают только Node.js startup-код и скрипты
  валидации. Секреты и URL базы данных не попадают в клиентский bundle.
- PostgreSQL будет источником истины для каталога и бизнес-данных. Схема не
  создаётся, пока для следующего этапа не утверждена модель данных.
- Excel, 1С, WordPress, загрузки файлов, админ-функции, пользователи, заявки,
  цены, корзина и бонусы находятся вне рамок этого foundation.

## Последствия

- Production-запуск блокируется, если обязательный URL PostgreSQL или публичный
  URL сайта отсутствует или не проходит проверку.
- `npm run start` является поддерживаемым путём запуска. Прямой `next start`
  также проверяет обязательную конфигурацию до запуска сервера.
- Каждое будущее изменение схемы выполняется через review миграции с явной
  оценкой отката.
- До публичного релиза хостинг должен предоставить HTTPS и проверенную Content
  Security Policy для утверждённых источников CMS и медиа.
- Окружения разработки и хостинга должны использовать Node.js 24.19.0 или
  более новый релиз ветки 24.x LTS.

## Миграция и откат

Это решение не меняет production-данные, базу данных, DNS, процесс на хостинге
или внешние системы. Если миграция не проходит обязательные проверки,
предыдущее статическое развёртывание остаётся нетронутым. Production-релиз
запрещён до проверки staging-развёртывания, конфигурации, миграций и health
endpoint.
